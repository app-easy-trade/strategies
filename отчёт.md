# Отчет по НИР: гибридный новостной парсер финансовых событий

## 1. Цель и постановка задачи

Цель НИР — разработать воспроизводимый прототип новостного парсера, который преобразует короткие финансовые сообщения в структурированные события для дальнейшей аналитики. В рамках работы рассматривается поток публичных постов MarketTwits: новости о компаниях, индексах, сырье, криптовалютах, ставках, геополитике и регуляторных событиях.

Основная задача системы: для каждого поста определить тему, связанные компании или рыночные инструменты, направление влияния, горизонт события, срочность, краткое объяснение и проверяемую цитату из исходного текста. Такой формат нужен для последующей фильтрации новостей, построения сигналов, ручного контроля и аналитических ноутбуков.

Проект не является торговым советником. Он решает более узкую исследовательскую задачу: проверить, можно ли построить прозрачный слой обработки новостного потока, где каждое решение имеет трассу инструментов и привязку к исходному тексту.

## 2. Данные

Источник данных — публичная web-страница Telegram-канала `https://t.me/s/markettwits`. Для воспроизводимости в репозитории сохранен локальный срез:

- `input/posts_sample.json` — корпус постов MarketTwits;
- `input/company_catalog.json` — мини-каталог компаний, тикеров, алиасов и секторных признаков;
- `input/market_rules.md` — правила классификации тем, горизонтов и направления влияния;
- `input/gold_eval.json` — размеченный набор для проверки качества.

Скрипт `fetch_markettwits.py` умеет обновлять корпус через публичную web-страницу Telegram без Telegram API. При загрузке HTML очищается от разметки, даты приводятся к ISO-формату, просмотры нормализуются в числа, хэштеги выделяются в отдельный список.

## 3. Архитектура системы

Пайплайн построен как гибрид правил, RAG-поиска, инструментов и структурированного вывода. Такой подход выбран для НИР потому, что в новостном парсинге важна не только точность итоговой метки, но и объяснимость: нужно понимать, почему система нашла тикер, откуда взяла цитату и какие шаги прошла.

Путь обработки одного поста:

1. `MarketPost` валидирует исходное сообщение, дату, текст, просмотры и хэштеги.
2. `retrieve_policy_context` подбирает релевантные правила и записи каталога через BM25.
3. `find_company_mentions` ищет компании и тикеры с учетом алиасов и границ токенов.
4. `classify_topic`, `extract_instruments`, `infer_impact` определяют тему, инструменты и влияние.
5. `NewsAnalysis` собирает результат в строгую Pydantic-схему.
6. `offline_judge` или `llm_judge` проверяет цитаты, числа и согласованность результата.
7. `pipeline.py` сохраняет итоговые JSON/CSV и трассу шагов.

Ключевые элементы контроля качества находятся в `schema.py`. Валидаторы проверяют, что дата публикации не находится в будущем, evidence-цитаты являются дословными фрагментами исходного текста, направленное влияние не выставляется без компании или инструмента, а знак `impact_score` соответствует классу влияния.

## 4. Реализация

Основной код расположен в корне репозитория:

- `fetch_markettwits.py` — сбор и нормализация постов;
- `rag.py` — поиск релевантного контекста по правилам и каталогу;
- `market_tools.py` — предметные инструменты для финансового текста;
- `agent.py` — агентная обработка одного поста и judge;
- `pipeline.py` — пакетная обработка корпуса;
- `eval.py` — измерение качества на размеченном наборе;
- `run_all.py` — единая точка запуска.

Система поддерживает два режима. Offline-режим работает без API-ключей и нужен для стабильной воспроизводимости. LLM-режим использует OpenAI-совместимый endpoint из `.env` и может применяться для более гибкого структурированного анализа и независимой проверки.

## 5. Оценка качества

Оценка выполняется на размеченных примерах из `input/gold_eval.json`. Проверяется не только финальная метка, но и путь обработки: какие инструменты были вызваны, сколько шагов потребовалось, появились ли ghost-цитаты или ghost-числа, какая оценочная стоимость прогона.

## 6. Ошибки и исправления

Во время разработки были выявлены несколько характерных ошибок, которые важны для новостного парсера.

1. В строке про индекс `IMOEX < 2400` ранняя версия находила тикер `MOEX` внутри `IMOEX` и ошибочно добавляла компанию Московская биржа. Исправление: для латинских тикеров добавлен match с границами, а хэштеги проверяются exact-match.

2. В новости про поставки энергетического угля слово `поставки` ошибочно срабатывало по маркеру `ставк`, из-за чего сырьевая новость попадала в `macro_rates`. Исправление: rate-маркеры заменены на более точные признаки, связанные с ЦБ, ФРС, ДКП, ОФЗ и индексом RGBI.

3. В посте с числом `2030` короткая сводка могла обрезать число и породить несуществующее значение. Исправление: обрезка summary теперь идет по ближайшему пробелу, чтобы не ломать числа.

Эти случаи сохранены в `output/failure_cases.json` и используются как регрессионные примеры для дальнейшей доработки.

## 7. Связь с исследовательскими ноутбуками

Папка `notebooks/` содержит дополнительные материалы НИР:

- `A_trade_by_trade.ipynb` — анализ сделок и связи с решениями;
- `B_signal_flow.ipynb` — анализ прохождения сигналов от raw-событий до submitted;
- `C_market_regime.ipynb` — сопоставление результатов с рыночным режимом.

Код парсера формирует структурированный слой новостей, а ноутбуки показывают, как этот слой может использоваться в более широкой исследовательской цепочке: от новостного события до сигнала, сделки и оценки рыночного контекста.

## 8. Ограничения

Система зависит от полноты `company_catalog.json`: если компания или тикер отсутствуют в каталоге, распознавание может быть неполным. Для постов с несколькими компаниями общий `impact` может сглаживать конфликт между разными эмитентами. Сарказм, мемные формулировки и очень короткие сообщения требуют ручного контроля. Без внешнего market-data tool система интерпретирует текст новости, но не проверяет фактическую реакцию цены.

## 9. Выводы

В рамках НИР получен рабочий прототип гибридного новостного парсера. Он загружает финансовые посты, нормализует их, извлекает компании и инструменты, классифицирует тему и влияние, сохраняет структурированные результаты и ведет трассу обработки. Отдельный judge снижает риск галлюцинаций за счет проверки цитат и чисел по исходному тексту.

Главный результат: для первого слоя мониторинга финансовых новостей гибридный подход оказывается практичным. Правила и каталог дают воспроизводимость, RAG добавляет предметный контекст, инструменты делают путь решения наблюдаемым, а структурированная схема и judge удерживают вывод в проверяемом формате.

Дальнейшие направления работы:

- расширить каталог компаний и алиасов;
- добавить внешний источник котировок и доходностей;
- считать отдельный `impact` для каждой компании в сложных постах;
- обновлять eval на новых срезах MarketTwits;
- связать результаты парсера с notebook-анализом сигналов и сделок.

## 10. Воспроизводимость

Полный запуск:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 run_all.py --offline --limit 40
```

Обновление корпуса:

```bash
python3 fetch_markettwits.py --limit 80 --out input/posts_sample.json
python3 run_all.py --offline --limit 40
```

Основные результаты сохраняются в `output/`, а отчет и README описывают актуальную версию проекта как НИР по новостному парсеру.
